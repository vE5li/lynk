# Nexus reads Rust with syn

## Decision

The `rust` provider of [nexus](nexus:nexus.self) parses source files with
[`syn`](nexus:cargo.dependency (Cargo.toml)), without its default features
([`nexus::providers::rust::items`](nexus:rust.module)). It builds
nothing and sees the source as written: inline modules and `#[path]` attributes, but
no items generated by macros.

## Why

[`nexus lint`](nexus:nexus.lint) runs before every change, so it has to
take milliseconds, not a build. Links point at definitions people wrote; generated code worth
linking to, like protobuf messages, is linked through the files it is
generated from, as
[`LintRequest`](nexus:protobuf.message (resources/nexus.proto)) is.

## Alternatives

- **rustdoc's JSON output**: complete (macros expanded, cfg resolved,
  re-exports), but needs a rustdoc build of every crate, tens of seconds
  cold for a mid-sized workspace, and its format is unstable.
- **rust-analyzer**, over LSP or as a library: complete as well, and could
  find the uses of an item, but has to index the workspace before a lint,
  and its library crates change every week.
- **Matching lines by hand**: no dependency, but misses inline modules,
  `#[path]` and declarations spanning lines.

A selector that needs macro-expanded items or the uses of an item can
switch to one of these without changing any link, since providers are
named after the language, not the backend.
